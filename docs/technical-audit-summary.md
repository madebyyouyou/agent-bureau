# 技术审计摘要

> 面向技术招聘者的公开版摘要。它保留原始完整性审计中的风险识别、证据链与架构决策，省略本机配置、真实会话数据和未公开环境信息。

## 审计范围与方法

本项目不是直接调用模型 API 的多 Agent 框架，而是在 CliDeck v1.31.24 提供的 PTY、WebSocket、转写和插件系统之上编排多个真实 CLI。集成前先对约 1.3 万行上游代码做静态逆向，按服务启动、PTY 生命周期、消息协议、Agent 间通信、遥测、转写、前端状态和插件系统拆成 8 份接口地图，再用契约测试、故障回放和受控运行验证关键假设。

审计遵循三条原则：

1. 从源码定位事实，不把 UI 表象当作接口保证。
2. 将“已验证事实”“合理推断”和“待验证假设”分开记录。
3. 优先使用上游插件 API；只有插件 API 无法覆盖的能力才进入受精确结构锚点守卫的幂等补丁。

详细接口证据见 [集成地图索引](integration-map-index.md)，最终形态见 [架构决定](architecture.md)。

## 关键风险与架构决策

| 风险 | 证据与影响 | 决策 |
|---|---|---|
| 本地控制面没有认证 | 上游 HTTP/WS 可向真实 CLI 写入输入；暴露到局域网会扩大为终端接管风险 | 默认只绑定 `127.0.0.1`，前端作为同源插件加载，不建议使用 `--host 0.0.0.0` |
| 多条异步回调可能重复投递 | 状态变化、超时器、watchdog 和菜单事件都可能同时唤醒调度 | 所有注入统一经过 `pump()`；回调只有唤醒权，没有直接发送权 |
| 忙碌状态下模拟回车可能误触权限菜单 | PTY 输入不是结构化 RPC；菜单检测又依赖终端画面 | 消息整条排队，空闲且无待处理菜单时才释放；菜单应答与普通消息走不同路径 |
| 菜单与干净转写依赖浏览器回传终端缓冲区 | 上游会发送 `terminal.capture`，无响应时权限卡和部分空闲检测会退化 | 每个工位维护隐藏终端模型并实现 `terminal.capture → terminal.buffer` 契约 |
| 工作状态信号跨 CLI 不一致 | Claude、Codex、Gemini 的 hook/OTLP 事件和收尾时序不同 | 复用上游各引擎状态机，业务层只消费统一的 `session.status`，并保留超时降级 |
| 会话工作目录不能由项目配置可靠推断 | 会话可被移动到其他项目，配置路径也可能为空或过期 | 通过插件会话 API 读取运行时 `cwd`，再用 Git 自身解析仓库根目录 |
| 上游升级可能让补丁静默错位 | 直接修改全局 npm 包会在升级后丢失，模糊替换还可能破坏新版本 | 主体能力留在独立插件；补丁使用精确锚点、结构漂移检测和幂等守卫，锚点漂移时明确失败 |
| 按轮回滚可能覆盖后续工作 | 成员可能连续修改同一文件，简单 reset/revert 会损伤后续轮次 | 保存每轮文件集合并检测交集；有重叠时拒绝单轮自动撤销，要求人工合并或选择整体回退 |
| 上下文占用无法跨供应商精确统一 | 上游只暴露部分遥测，压缩后累计 token 也不等于当前上下文占用 | v0.6.1 只展示明确标注为“约”的估算值，不伪装成精确计量 |

## 代表性审计结论

### 1. 信任边界必须停在回环地址

浏览器 Origin 检查不是身份认证；无 Origin 的本地客户端仍可连接。由于一个 WebSocket 消息就能向 PTY 写入内容，最安全的部署边界是单机回环网络。插件与上游 UI 同进程、同端口，既解决跨域问题，也避免额外开放控制 API。

### 2. 浏览器是协议参与者，不只是渲染层

上游的菜单检测会主动要求客户端返回可见终端行。若只实现聊天 UI 而忽略该往返，权限菜单、等待状态和转写提交会静默退化。因此本项目把隐藏终端视为协议适配器，而不是可选的显示组件。这一结论直接改变了前端架构。

### 3. 调度正确性优先于吞吐

多个 Agent 可以并行消化同一条群消息，但公开发言按顺序串行。调度器采用“消化—发言”两阶段状态机，消息、回执、超时和熔断都汇入单一泵入口，从结构上避免多路定时器同时按下 Enter。该设计牺牲少量峰值吞吐，换取可解释、可回放的协作顺序。

### 4. 插件优先，补丁最小化

会话枚举、转写、状态、菜单、前后端消息等能力都走上游插件 API。补丁只承担插件 API 尚未提供的启动参数拼接和少量兼容挂钩，实际业务逻辑仍位于仓库内。测试会把补丁套用到 `vendor/clideck` 固定版本副本，并验证重复执行不产生二次修改。

### 5. 自动回滚需要业务语义

“每轮一次 Git 提交”只能建立追踪基础，不能自动保证回滚安全。系统额外记录相邻轮次的文件集合；当某轮文件已被后续成员继续修改时，不执行看似方便但可能丢数据的自动撤销。这体现了 Human-in-the-Loop 的边界：系统负责识别风险并阻止危险默认值，人负责处理真实语义冲突。

## 验证策略

- 纯函数测试覆盖信封解析、消息排序、终端文本清洗、回执识别和 ask 尾注剥离。
- 假时钟测试覆盖轮次推进、忙碌队列、超时、watchdog 和熔断。
- 契约测试锁定插件前后端消息格式与模板渲染。
- 补丁测试在固定的上游源码副本上执行，并包含历史事故的端到端回放。
- 仓库卫生测试锁定可移植启动路径、公开作者身份、默认配置和包锁一致性。

## 公开快照处理

公开版只保留可解释架构与复现实验所需的信息：

- 本机用户名、真实绝对路径、账号邮箱、访问凭据、代理地址和会话标识不进入源码与文档。
- 设计原型保留为作品集材料；自动生成的 Agent 操作说明不作为项目文档发布。
- 上游副本固定为 CliDeck v1.31.24，保留原始 MIT 许可证，并在仓库根目录提供第三方声明。
- 未被代码或文档引用的大型演示 GIF 不进入发布快照。

## 当前边界

这是 Windows 本地可运行原型，不是多租户服务。运行者仍需自行安装并登录所使用的 CLI；项目不会分发或收集这些工具的凭据。若未来需要远程访问、多人共享或云端部署，应先补充独立认证、授权、审计日志和传输安全设计，而不能直接扩大当前监听地址。
