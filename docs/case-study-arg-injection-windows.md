# 案例：被命令行绞碎的系统提示

> 一个静默失效的注入链路：席位身份注入在 Windows 上从未真正生效，而系统的自检机制一直报告成功。
> 本文记录现象、根因、证据与修复，作为「不要把进程存活当作交付成功」的工程样本。

## 背景

本项目把团队章程和角色卡注入各 CLI 的**系统提示层**，而不是作为普通对话消息发送。理由是系统提示不参与上下文压缩，成员在长会话里不会忘记身份与协作协议。

实现方式是改写 CLI 的启动参数：

| 引擎 | 注入方式 |
|---|---|
| claude 系（含中转席） | `--append-system-prompt <章程全文>` |
| codex | `-c developer_instructions=<章程全文>` |

章程全文约 4 KB，内含协议标签 `<group_message>` `<pass />`、成对引号，以及上百个换行。

## 一、故障现象

同一个根因在两类引擎上呈现出**完全不同**的症状，这是排查最初被误导的原因。

**codex 席位——响亮地崩溃。** 用户点「接续上岗」后界面先提示「已带记忆接回」，约一秒后立刻变成「工位已关闭（进程退出或被移除）」。手工复现可见进程退出码 1，终端只留一行：

```
系统找不到指定的文件。
```

「全新上岗」路径同样必死，因此这不是会话接续（resume）本身的问题。

**claude 席位——静默地降级。** 工位正常启动、界面显示「在岗」、能收发消息，**但系统提示里只有章程的第一行**。没有任何报错。从外部观察，成员表现为"不太守协作协议"，很容易被误判成模型能力问题。

**放大故障的第三个因素**：注入是否成功由一个门控函数判定，而它的判据是"补丁装没装 + 章程包文件在不在"，**从不验证参数是否真的抵达进程**。门控恒为真，于是三处会话内补发兜底（入职全文 / 接续补发 / 压缩后补发）全部被跳过。结果是：注入悄悄失败，兜底又被自己关掉，所有席位都在没有章程的状态下运行。

## 二、根因

Windows 上，上游为了让 `codex`、`claude` 这类无扩展名命令能被 PATHEXT 解析，把每条启动命令都包了一层：

```js
// 上游 utils.js
if (process.platform === 'win32' && !parts[0].match(/\.(exe|com)$/i) && ...) {
  return [process.env.COMSPEC || 'cmd.exe', '/c', ...parts];
}
```

而 `cmd.exe` 的命令行解析有三条与本场景致命冲突的规则：

1. **只把双引号 `"` 当引号**。单引号、TOML 的三引号对它都是普通字符，提供零保护。
2. **`< > | &` 是元字符**，在引号外出现即按重定向/管道处理。
3. **遇到真实换行即截断命令行**，其后内容被丢弃。

章程恰好三样全占。两种死法由此而来：

- **codex**：参数值经 `JSON.stringify` 编码后是单行（换行转义为 `\n`），躲过了规则 3。但 JSON 会在值外再包一对引号，且把内部引号转义成 `\"`——`cmd.exe` 不认反斜杠转义，只数引号个数，于是引号配对整体错位，`<group_message>` 落到"引号外"，被当作输入重定向。cmd 去找一个名为 `group_message` 的文件，失败，退出码 1。
- **claude**：参数值是**明文多行**，直接撞上规则 3，在第一个换行处被截断。

> 值得注意的是：上游自己的 GUIDE 文本（单行、仅两对尖括号）**能正常送达**。它能活下来纯属内容运气——引号位置恰好让尖括号留在引号内。一旦拼上章程，引号奇偶被打乱，整条链路就崩了。**这类"靠内容运气成立"的机制，是最危险的一种技术债**：它不会在测试里失败，只会在内容变化时突然失败。

## 三、排查证据

### 3.1 对照实验：锁定变量

在受控 PTY 里复刻上游真实 argv 构造，只改一个变量：

| 实验 | 结果 |
|---|---|
| 仅上游 GUIDE + resume | ✅ 正常启动 |
| GUIDE + 章程 + resume（故障现状） | ❌ 退出码 1，1030 ms，「系统找不到指定的文件」 |
| GUIDE + 章程（**删去所有 `<` `>`**）+ resume | ✅ 正常启动 |
| GUIDE + 章程 + **全新启动**（无 resume） | ❌ 同样暴毙 |
| 仅上游 GUIDE + 全新启动 | ✅ 正常启动 |

第 3 行锁定元凶是尖括号；第 4 行排除了 resume 这个最初的怀疑对象。

### 3.2 关键教训：进程"存活"不等于参数"送达"

排查中途曾把参数值改成 TOML 多行字面量 `'''…'''`，观察到进程能存活 15 秒，一度判定修复成功。**这是误判。**

后续用 codex 自带的 `codex debug prompt-input`（打印模型可见的完整提示词，不消耗额度）核对，发现输出与不注入任何参数时**逐字节相同**——章程根本没进去。进程之所以存活，是因为命令行在换行处被截断后，`resume` 子命令连同章程一起被丢弃，codex 退化成了交互模式的空会话。

> **该修复方案被证伪并回滚。** 单引号系字面量对 `cmd.exe` 无效（规则 1），多行形式又撞上规则 3。

同时验证了另外两条死路：codex 0.144.6 对 `experimental_instructions_file` 和 `instructions_file` **静默忽略**（"能启动"同样不能作为证据）。

### 3.3 量化两类症状

对 claude 路径，用一个只打印自身 argv 的替身程序，比对同一份真实章程的抵达情况（SHA-256 前 16 位）：

| 传参路径 | 收到长度 | 一致性 |
|---|---|---|
| 穿 `cmd.exe /c`（故障现状） | **22 字符** | ❌ 只剩第一行 |
| 直接 spawn（修复后） | **4181 字符** | ✅ 逐字节一致 |

4181 → 22，这就是"静默降级"的量化形态。

## 四、技术方案

### 4.1 绕开 cmd.exe

`cmd.exe` 存在的唯一理由是 PATH 解析。既然如此，**按 Windows 的 `PATH` + `PATHEXT` 顺序解析出真实可执行文件，直接 spawn**——node-pty 会走 Windows 正规 argv 传参，`cmd.exe` 那套解析彻底不参与，尖括号、引号、换行都只是普通字节。

做法是读取 npm 生成的 `.cmd` 壳子（格式稳定，可解析），问出真身：

```
claude → …\node_modules\@anthropic-ai\claude-code\bin\claude.exe
codex  → <node.exe> …\node_modules\@openai\codex\bin\codex.js
```

随后把 `['cmd.exe', '/c', <命令>]` 三件套整体替换为真身前缀，其余参数相对顺序不变。若壳子解析失败（非 npm 布局、命令不在 PATH 等），**放弃挂旗**而不是挂一面残缺的旗。

实现见 [`app/plugin/kfq-spawn.js`](../app/plugin/kfq-spawn.js)。解析结果按 `命令名 + PATH + PATHEXT` 缓存，任一环境值变化都会重新解析。

### 4.2 让门控说实话

根因分析暴露出比 bug 本身更值得修的设计缺陷：**自检机制检查的是"前置条件是否具备"，而不是"操作是否成功"**。

改为**spawn 回执**：注入函数只准备改写后的 argv 和提交/撤销回调；上游 `pty.spawn` 成功返回后才写回执，参数无法安全改写或 spawn 抛错时删除回执。门控改读这个结果，于是"参数没送进新进程"能被系统感知并自动退回会话内补发——宁可多发一遍章程，也不允许席位在自己以为有章程的情况下裸奔。

这里刻意不把回执描述成"模型已经消费提示"：它证明的是 node-pty 已创建进程并接受改写后的 argv。CLI 内部是否采纳合法参数，仍由事故回放中的 argv 替身和 `codex debug prompt-input` 等端到端探针验证。

```js
term = pty.spawn(kfq.parts[0], kfq.parts.slice(1), options);
kfq.commit?.(); // 只在 pty.spawn 成功返回后提交
```

### 4.3 回归测试

新增一组回归用例（总数 100+）：

- **认路矩阵**：用临时目录里伪造的 npm 壳子 + 改写 PATH/PATHEXT 做确定性验证，不依赖跑测机器是否安装了 CLI；覆盖 `.com` / `.exe` 直连、`node + .js` 壳子、扩展名优先级变化，以及带额外参数的中转席。
- **降级路径**：命令无法解析时必须原样返回、不得挂旗。
- **回执状态**：apply 阶段不写、spawn 成功后提交、spawn 异常可撤销，用户自定义系统提示/绕不开/空章程包时删除陈旧回执。
- **不变式断言**：改写后的 argv 中不允许再出现 `cmd`。

补丁标记升级为 v2；启动脚本会把已安装的 v1 补丁原位升级并补上 commit/rollback，重复执行仍是 no-op。

## 五、可迁移的结论

1. **"进程起来了"不是交付成功的证据。** 需要能直接观测最终状态的探针——本例中 `codex debug prompt-input` 与 argv 替身程序，两者都零成本、可重复。
2. **自检要检查结果，不要检查前置条件。** 检查"补丁装了吗"永远不等于"注入成功了吗"，而错误的自检会连带关掉本来有效的兜底，把可恢复故障放大成系统性故障。
3. **同一根因可以有截然不同的症状。** 一个响亮崩溃、一个静默降级，容易被当成两件事分别排查。静默的那个危害更大。
4. **警惕"靠内容运气成立"的机制。** 它在测试里永远是绿的，直到内容变化的那一天。
5. **降级要显式设计。** 每个"我放弃了"的分支都必须留下可被系统读到的痕迹，否则降级路径本身就是下一个静默故障。
